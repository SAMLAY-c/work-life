# 需求分析【20-23】
```text
原始需求 → [角色] → [场景] → [目的] → 产品方案
```
### 1. 角色（Who）
**定义：** 需求的发起方与相关利益方

| 维度         | 关键问题                   | 示例（直播间案例）     |
| :--------- | :--------------------- | :------------ |
| **角色关系**   | 他们之间如何互动？              | 1v1教学 或 1v多教学 |
| 区分提出者vs使用者 | 外教提的需求，可能源自学生痛点        |               |
| 多角色并列分析    | 如直播间：老师（教学）、学生（学习）需求不同 |               |
| 角色画像细化     | 身份、能力、使用习惯、痛点预判        |               |

✅ 输出：角色清单 + 各角色核心诉求假设
**要点：** 同一功能，不同角色的使用方式和出发点完全不同。
### 2. 场景（Where/When/What）
**定义：** 用户在什么情况下，做了什么事，遇到了什么阻碍
**场景的描述公式：**
> 「在 [特定环境] 中，当 [用户状态] 时，想要 [完成某事]，但因 [现有局限] 导致 [具体痛点]」
**示例：**
> 在直播上课过程中，当学生听到不懂的知识点时，想要立即提问答疑，但因没有文字输入功能，只能憋着无法反馈。
- **如何提炼场景（方法论）**：
1️⃣ 产品沉浸：亲自使用产品，建立真实认知
2️⃣ 换位思考：「如果我是TA，此刻会怎么做？」
3️⃣ - **模拟流程**：模拟用户从“开始”到“结束”的全过程。
            - _案例推演_：老师上班 -> 打开网页登录 -> 开摄像头 -> 打开PPT -> 开始讲课 -> 发现学生听不懂 -> 需要互动/答疑。
4️⃣ 头脑风暴：穷举可能的使用情境（定性）
- **场景与功能的关系**：
    - 一个场景可能对应一个目的。
    - 多个场景可能最终对应同一个目的（此时一个功能即可解决多个场景问题）。
### 3. 目的（Why）
- **定义**：用户在做这件事时，最终想要达到的效果是什么。
- **关键逻辑**：
    - **目的必须挂钩场景**：单纯问“目的是什么”容易跑偏，必须结合具体场景来问。
    - **区分“方案”与“目的”**：
        - 用户提的往往是“方案”（如：我要打字功能）。
        - 产品经理要挖掘的是“目的”（如：为了实时答疑）。
        - **关键原则**：目的必须从场景中推导，避免脱离情境空想

| 表面需求     | 可能隐藏的真实目的         |
| -------- | ----------------- |
| 「加个打字功能」 | 学生想即时提问，不打断教学节奏   |
| 「加个举手按钮」 | 一对多场景下有序互动，避免语音混乱 |
| 「邀请语音功能」 | 增强互动感/进行口语练习/确认理解 |

✅ 输出：每个场景对应的核心目的（用「为了…」句式表达）

#   需求澄清方法论
## 一、先回答核心焦虑：「我是不是想多了？」
```
❌ 错误认知：澄清和分析是两套独立流程，必须严格按顺序执行
✅ 正确认知：澄清是「验证假设」，分析是「构建逻辑」，两者交替进行
```
### 🔄 真实工作流是这样的：
```
拿到需求
   ↓
【10分钟快速自检】← 你担心的"白做"其实发生在这里
   ├─ 角色：谁提的？谁在用？（列1-2个假设）
   ├─ 场景：大概什么情况下用？（写1句场景描述）
   ├─ 目的：用户说的方案背后，可能想要什么？（猜1个目的）
   └─ ✨关键：同时标记「我不确定的3个点」
   ↓
【带着假设+不确定点去沟通】← 澄清的主战场
   ├─ 用自然话术验证你的假设："我理解这个功能主要是给XX用的，对吗？"
   ├─ 重点追问不确定点："您刚才说的迟到，具体是指哪个环节？"
   ├─ 倾听中动态修正你的角色/场景/目的框架
   ↓
【回到分析】← 信息充足后正式启动
   └─ 用完整的角色-场景-目的框架，推导产品方案
```
> 💡 关键认知：**那10分钟自检不是白做，而是让你问出高质量问题**。没有假设的提问，容易变成漫无目的的闲聊。


## 二、防「自以为理解」的3道保险机制

### 🔒 保险1：强制输出「不确定性清单」
每次沟通前，必须写下：
```
✅ 我确定的事实（来自需求原文）：
   - 例：外教提出需要打字功能

❓ 我不确定的假设（需要验证）：
   - 例：我假设是学生听课时有疑问，但不确定是否还有其他场景
   - 例：我假设打字是为了不打断教学，但不确定是否有录屏回放等替代方案

🎯 本次沟通必须搞清楚的Top3问题：
   1. 学生提问的频率和典型场景是什么？
   2. 目前没有打字功能时，师生怎么解决这个问题？
   3. 除了打字，用户是否考虑过其他互动方式？
```

### 🔒 保险2：沟通中强制「复述确认」
每聊完一个关键点，用这个句式：
> "我理解一下，您刚才说的是【复述内容】，我的理解对吗？"

**作用**：
- 避免你脑补对方没说的话
- 给对方纠正你理解偏差的机会
- 让对话节奏更清晰，不跑偏

### 🔒 保险3：区分「事实」vs「推测」的笔记法
沟通记录分两栏：

| 事实（对方原话/可验证信息）       | 推测（我的理解/待验证假设）    |
| -------------------- | ----------------- |
| "学生经常因为不敢开口而错过提问"    | → 可能是文化差异导致的表达障碍  |
| "目前用聊天窗口打字，但被其他消息淹没" | → 需要独立于聊天区的专用提问通道 |

> ✨ 每周回顾：统计你的"推测"有多少被验证为真，持续校准判断力

## 三、澄清 vs 分析：一张表讲透区别

| 维度       | 需求澄清               | 需求分析                |
| -------- | ------------------ | ------------------- |
| **核心目标** | 验证「需求是什么+为什么」      | 推导「产品怎么做」           |
| **思维模式** | 向外求：提问、倾听、验证       | 向内求：推理、拆解、构建        |
| **关键动作** | 问Why、复述确认、标记不确定    | 画角色关系、写场景故事、映射目的    |
| **产出物**  | 清晰的需求背景文档+待验证假设清单  | 产品方案原型+功能逻辑说明       |
| **判断标准** | "我和需求方对问题的理解一致了吗？" | "这个方案能闭环解决验证过的问题吗？" |

### 🎭 类比理解：
```
澄清 = 医生问诊：
   - 问症状、听描述、做检查
   - 目标：确诊"是什么病"

分析 = 医生开方：
   - 根据诊断，设计治疗方案
   - 目标：解决"怎么治病"

❌ 错误做法：病人说"我头疼"，医生直接开止痛药（没问诊就开方）
✅ 正确做法：先问"哪里疼/多久了/什么情况下疼"，确诊后再开药
```


## 四、实操指南：如何让方法论「隐形」融入对话
你担心"带着方法论去问会显得刻意"，解决方案是：**把框架转化成自然语言**
### 🔄 4问法 → 自然话术对照表：

| 方法论维度    | 生硬问法（❌避免）      | 自然问法（✅推荐）                  |
| -------- | -------------- | -------------------------- |
| **Why**  | "您的业务目标是什么？"   | "如果这个功能上线了，您希望看到什么变化？"     |
| **Who**  | "请区分需求提出者和使用者" | "这个功能主要是老师用，还是学生也会直接操作？"   |
| **What** | "请描述您的使用场景"    | "能跟我讲讲上次遇到这个问题时，具体发生了什么吗？" |
| **How**  | "您目前的解决方案是什么？" | "现在没有这个功能时，大家是怎么凑合解决的？"    |

### 💡 高阶技巧：用「故事引导」代替「框架提问」
```
❌ "请用角色场景目的法描述您的需求"

✅ "我试着还原一下场景，您看对不对：
   周三晚上8点，外教正在直播上课，有个学生听到一个知识点没懂，
   想马上问一下，但发现没法打字，只能等课后发消息，
   这时候老师可能已经讲下一页了，学生的问题就错过了...
   您遇到的情况是这样吗？还是有其他场景？"
```
→ 用故事激发对方补充细节，比直接问框架更高效

## 五、给你的专属SOP：防自以为是检查清单
### 📋 每次需求沟通前，花10分钟完成：
```
【Step 1】快速自检（5分钟）
□ 用1句话复述原始需求
□ 列出角色/场景/目的各1个假设
□ 标记3个最不确定、必须问清楚的点

【Step 2】沟通中（动态执行）
□ 每聊完一个模块，用"我理解的是..."复述确认
□ 听到新信息，立即标注：这是事实 or 我的推测？
□ 如果对方说的和你假设差异>50%，暂停分析，先澄清

【Step 3】沟通后（5分钟复盘）
□ 更新不确定性清单：哪些已解决？哪些仍需跟进？
□ 检查：我的假设有多少被验证？偏差在哪里？
□ 决定：信息是否足够进入正式分析？如果不确定点>3个，预约二次澄清
```
### 🚦 决策树：什么时候该暂停分析，回头澄清？
```
如果满足以下任一条件 → 立即暂停，先澄清：
□ 同一个问题，不同干系人给出矛盾答案
□ 你无法用1句话向同事讲清楚"这个需求要解决什么问题"
□ 设计方案时，发现需要假设"用户应该会..."但无依据
□ 业务方说"这个很简单"，但你完全想象不出使用画面
```

## 六、最后送你一句心法

> 🔑 **"澄清不是为了证明我懂了，而是为了发现我哪里没懂"**
你担心"自以为是"，恰恰说明你有产品人的敏感度。真正危险的，是那些从不怀疑自己理解的人。
**方法论不是枷锁，而是安全网**：
- 它帮你系统化地"查漏"，而不是替代思考
- 它让你问得更准，而不是问得更多
- 它保护你不被表面需求带偏，而不是让你变得教条
### 🎁 附：新手友好版「澄清话术模板」
```
开场：
"关于这个需求，我想先跟您确认几个细节，确保我理解的和您想的一致~"

挖Why：
- "如果这个功能做成了，您最希望看到的3个变化是什么？"
- "如果不做这个，目前最大的困扰会持续吗？"

挖场景：
- "能跟我讲讲最近一次遇到这个问题时，具体发生了什么吗？"
- "当时您/用户第一反应是想怎么解决？"

验证假设：
- "我猜这个功能主要是为了解决XX问题，我的方向对吗？"
- "刚才您说的A和B，哪个对业务影响更大？"

收尾确认：
"我总结一下今天确认的重点：1...2...3...，还有哪里我理解偏差的吗？"
```
