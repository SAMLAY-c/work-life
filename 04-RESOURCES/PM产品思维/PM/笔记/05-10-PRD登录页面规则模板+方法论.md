# 📦 第一部分：登录页面PRD规则模板（可直接复用）

## 1. 页面元素清单

| 元素 | 类型 | 必填 | 默认值 | 备注 |
|------|------|------|--------|------|
| 手机号输入框 | 数字输入 | 是 | 空 | 11位，仅数字 |
| 获取验证码按钮 | 按钮 | 是 | "获取验证码"，禁用态 | 依赖手机号校验 |
| 验证码输入框 | 数字输入 | 是 | 空 | 4位/6位，仅数字 |
| 登录按钮 | 提交按钮 | 是 | "登录"，禁用态 | 表单校验后启用 |
| 用户协议勾选 | 复选框 | 是 | 未勾选 | 文案+跳转链接 |

## 2. 输入框规则（通用）

### 手机号输入框
```markdown
【字符规则】
- 仅允许输入数字（0-9），其他字符自动过滤/无法输入
- 最大长度：11位，超出部分无法输入

【交互规则】
- 输入时：实时校验格式，格式错误时输入框边框变红（可选）
- 失焦时：若内容非空且格式错误，提示"手机号码格式不正确"
- 支持粘贴：粘贴内容自动过滤非数字字符，并按11位截断

【提示文案】
- 占位符："请输入手机号码"
- 格式错误："手机号码格式不正确，请重新输入"
- 长度错误："请输入11位手机号码"
```

### 验证码输入框
```markdown
【字符规则】
- 仅允许输入数字（0-9）
- 固定长度：{{验证码位数}}位（如4/6），由产品配置

【交互规则】
- 仅当"获取验证码"成功发送后可输入
- 支持粘贴数字，粘贴后自动校验长度
- 输入满{{位数}}位后，可自动聚焦登录按钮（体验优化，可选）

【提示文案】
- 占位符："请输入{{位数}}位验证码"
- 长度不足："请输入{{位数}}位验证码"
- 内容错误："验证码错误，请重新输入"
- 已过期："验证码已失效，请重新获取"
```


## 3. "获取验证码"按钮规则

```markdown
【初始状态】
- 默认文案："获取验证码"
- 默认状态：禁用（置灰，不可点击）
- 启用条件：手机号输入框 = 11位数字 + 格式校验通过

【点击后流程】
1. 调用发送短信接口
2. 接口成功：
   - 按钮文案变为："{{倒计时}}s后重新获取"
   - 开始倒计时（默认60秒，可配置）
   - 倒计时期间按钮禁用，不可重复点击
3. 接口失败：
   - 保持原状态
   - Toast提示失败原因（如"发送失败，请检查网络"）

【倒计时结束】
- 文案恢复："获取验证码"
- 状态恢复：可点击（仍需满足手机号校验条件）

【异常场景】
- 网络异常：提示"网络连接异常，请重试"
- 手机号未注册/已注册：按业务逻辑提示（登录/注册场景区分）
- 请求频繁：提示"操作过于频繁，请稍后再试"（前端防抖+后端限流）

【⚠️ 重要逻辑】
- 验证码有效期：{{X}}分钟（如10分钟），与按钮倒计时无关
- 重新发送新验证码后，上一条验证码立即失效
```

## 4. "登录"按钮规则（表单提交）

```markdown
【初始状态】
- 默认文案："登录"
- 默认状态：禁用
- 启用条件（同时满足）：
  ✓ 手机号：11位 + 格式正确
  ✓ 验证码：{{位数}}位数字
  ✓ 用户协议：已勾选（如有）

【点击提交流程】
1. 前端本地校验（按优先级，一次只提示一个错误）：
   ① 手机号格式错误 → 提示"手机号码格式不正确"，聚焦手机号框
   ② 验证码长度不足 → 提示"请输入{{位数}}位验证码"，聚焦验证码框
   ③ 协议未勾选 → 提示"请阅读并同意用户协议"，聚焦勾选框

2. 本地校验通过后：
   - 按钮显示loading状态，禁用防止重复提交
   - 调用登录接口，传入：手机号 + 验证码

3. 接口返回处理：
   ✅ 成功：
      - Toast提示"登录成功"
      - 延迟{{200}}ms后跳转至{{首页/原页面}}
      - 本地存储token/用户信息
   
   ❌ 失败：
      - 验证码不匹配 → "验证码错误，请重新输入"，清空验证码框并聚焦
      - 验证码过期 → "验证码已失效，请重新获取"，聚焦获取按钮
      - 账号异常（封禁/未注册）→ 按业务规则提示
      - 网络异常 → "网络连接异常，请检查后重试"（全局统一文案）
      - 其他错误 → 显示接口返回errorMsg，或兜底文案"登录失败，请稍后重试"

【安全限制】（后端配合）
- 同一手机号登录请求：{{1}}分钟内最多{{5}}次，超限锁定{{15}}分钟
- 验证码连续错误{{5}}次：该手机号临时锁定，防止暴力破解
```

## 5. 用户协议模块

```markdown
【展示规则】
- 文案："登录即同意《用户协议》《隐私政策》"
- 《》内文字为可点击链接，跳转对应H5页面

【勾选规则】
- 复选框默认状态：{{未勾选}}（按法务要求配置）
- 点击复选框：切换勾选/取消状态
- 点击协议文字：跳转协议页，不改变勾选状态

【校验规则】
- 未勾选时点击登录 → 提示"请阅读并同意用户协议"
- 提示后自动聚焦勾选框（提升操作效率）
```

## 6. 全局异常处理（可复用）

```markdown
【网络异常】
- 所有接口请求超时/失败时，统一提示："网络连接异常，请检查后重试"
- 建议：在PRD开头定义全局异常文案，避免重复撰写

【页面异常】
- 白屏/崩溃：展示缺省页 + "页面走丢了，点击刷新"
- 接口5xx错误：Toast提示"服务繁忙，请稍后重试"

【数据兜底】
- 手机号/验证码输入框：禁止输入emoji、特殊符号、空格
- 所有提示文案：避免技术术语，使用用户可理解的自然语言
```

# 🧠 第二部分：PRD规则撰写方法论（可迁移框架）

> 核心思想：**结构化思维 + 状态穷举 + 用户视角**


## 一、通用撰写流程（4步法）

```
📐 Step 1：拆解页面元素
   ↓
   列出所有可交互组件：输入框/按钮/勾选/链接/提示区...
   → 输出：元素清单表（含类型、必填、默认值）

📐 Step 2：定义单组件规则（先静态，后动态）
   ↓
   对每个元素按顺序写：
   • 静态规则：初始状态、禁用条件、显示文案
   • 动态规则：用户操作后的反馈、状态流转、边界处理
   → 输出：组件规则卡片（可复用模板）

📐 Step 3：串联交互流程（先正常，后异常）
   ↓
   • 正常流：用户理想操作路径，一步步写清楚跳转/反馈
   • 异常流：按优先级列举典型错误场景 + 对应提示
   → 输出：流程图 + 异常对照表

📐 Step 4：补充全局规则 & 边界说明
   ↓
   • 通用异常：网络/超时/服务错误（建议全局统一定义）
   • 安全限制：防刷/防暴/频控（标注前后端分工）
   • 文案规范：统一语气、避免歧义、预留多语言空间
   → 输出：全局规则附录
```

---

## 二、规则描述万能句式（直接套用）

### 1. 状态描述
```
✅ 当【条件】时，【元素】处于【状态】，表现为【视觉/交互反馈】
❌ 当【条件】不满足时，【元素】禁用/置灰/隐藏，提示【文案】
```

### 2. 操作反馈
```
用户点击【按钮】后：
1. 先校验【前置条件】→ 不满足则提示【文案】并聚焦【字段】
2. 校验通过后 → 显示【loading/禁用】，调用【接口】
3. 接口返回成功 → 执行【跳转/刷新/提示】
4. 接口返回失败 → 保留当前页，提示【具体错误】，【可重试】
```

### 3. 异常处理
```
若出现【异常类型】：
- 用户可见：Toast/弹窗提示【友好文案】
- 系统行为：记录日志 + 【重试/降级/兜底】
- 恢复路径：引导用户【重新操作/检查网络/联系客服】
```

### 4. 表单校验通用逻辑
```
提交时校验顺序（按用户体验优先级）：
1️⃣ 非空校验 → 2️⃣ 格式校验 → 3️⃣ 业务规则校验 → 4️⃣ 接口校验
❗ 原则：一次只提示一个错误，聚焦第一个错误字段，避免信息过载
```


## 三、状态穷举清单（防遗漏检查表）

写规则时，对每个交互元素问自己：

```
🔹 按钮类：
   □ 初始态（禁用/启用？）
   □ 点击态（loading/防重复？）
   □ 成功态（跳转/提示？）
   □ 失败态（错误文案？可重试？）
   □ 边界态（倒计时/频控/权限？）

🔹 输入框类：
   □ 空状态（占位符？校验时机？）
   □ 输入中（实时校验？字符过滤？）
   □ 失焦时（格式校验？错误提示？）
   □ 粘贴支持（是否允许？如何过滤？）
   □ 长度边界（最小/最大？超出处理？）

🔹 流程类：
   □ 正常路径：每一步的输入→处理→输出是否闭环？
   □ 异常路径：网络/数据/权限/超时是否都有兜底？
   □ 中断恢复：用户中途退出/刷新，状态是否可恢复？
```

## 四、可迁移的3个核心思维

### 1. 组件化思维
> 同类规则写一次，其他"同XX组件，仅参数不同"
```
✅ 示例：
"验证码输入框规则同手机号输入框，仅：
- 长度改为4位
- 移除格式校验（纯数字）
- 增加'与发送验证码匹配'的业务校验"
```

### 2. 状态机思维
> 任何交互元素 = 有限状态 + 状态转移条件
```
✅ 示例：获取验证码按钮
[禁用] --(手机号正确)--> [可点击] --(点击+接口成功)--> [倒计时] 
[倒计时] --(60s结束)--> [可点击]
[任意状态] --(网络失败)--> [保持原态+提示错误]
```

### 3. 用户视角思维
> 每条规则问自己：用户看到这个提示，知道下一步该做什么吗？
```
❌ 技术语言："校验失败，errorCode:1001"
✅ 用户语言："验证码错误，请重新输入" + 自动聚焦输入框

❌ 模糊提示："操作失败"
✅ 明确引导："发送失败，请检查网络后重试" + "重试"按钮
```
## 五、PRD自检清单（写完必查）
```
□ 所有交互元素是否都有"初始状态"定义？
□ 所有按钮点击是否有"前置校验+后置反馈"闭环？
□ 异常提示是否具体、可操作、无技术术语？
□ 是否标注了前后端分工（如频控/校验由谁实现）？
□ 文案是否统一（如"验证码"vs"校验码"）？
□ 是否预留了配置项（如倒计时时长/验证码位数）？
□ 是否考虑了无障碍/多语言/低端机兼容？（进阶）
```
