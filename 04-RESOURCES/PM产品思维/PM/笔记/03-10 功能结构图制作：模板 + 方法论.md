
## 一、可直接套用的模板（正常模板）

### 🔹 功能结构图标准模板

```
[产品名称] 功能结构图
│
├─ 📦 模块A：[按业务对象/场景分类]
│  ├─ ▶ 子模块A1
│  │  ├─ ✓ 功能1：[动词+名词] 如「展示图片」
│  │  ├─ ✓ 功能2：如「编辑图片」
│  │  └─ ✓ 功能3：如「删除图片」
│  │
│  └─ ▶ 子模块A2
│     ├─ ✓ 功能1：如「分享视频」
│     └─ ✓ 功能2：如「下载视频」
│
├─ 📦 模块B：[按业务对象/场景分类]
│  ├─ ▶ 子模块B1
│  │  ├─ ✓ 功能1：如「搜索内容」
│  │  └─ ✓ 功能2：如「筛选排序」
│
└─ 📦 通用模块
   ├─ ✓ 用户登录
   ├─ ✓ 设置偏好
   └─ ✓ 帮助反馈
```

### 🔹 填写规范速查表

| 要素     | 规范说明               | 示例 ✅            | 示例 ❌          |
| ------ | ------------------ | --------------- | ------------- |
| **层级** | 产品→模块→子模块→功能（按需扩展） | 相册→图片操作→编辑      | 直接罗列功能无归类     |
| **命名** | 功能项以「动词+名词」为主      | 分享图片、删除视频       | 图片分享功能、视频删除模块 |
| **粒度** | 一个功能=一个用户可执行的最小操作  | 编辑、收藏、下载        | 图片管理（太模糊）     |
| **范围** | 先罗列完整功能，暂不考虑页面/交互  | 先写"编辑图片"，再想怎么编辑 | 边想功能边画原型      |

### 🔹 实战示例：手机相册功能结构图

```
📱 手机相册
│
├─ 🖼️ 媒体展示
│  ├─ ✓ 展示图片（缩略图/大图/全屏查看）
│  ├─ ✓ 展示视频（播放/暂停/进度控制）
│  └─ ✓ 展示动图（自动播放/手动播放）
│
├─ ✏️ 图片操作
│  ├─ ✓ 编辑图片（裁剪/滤镜/调色）
│  ├─ ✓ 分享图片（微信/微博/链接）
│  ├─ ✓ 删除图片（单删/批量/回收站）
│  └─ ✓ 收藏图片（加星标/移入相册）
│
├─ 🎬 视频操作
│  ├─ ✓ 编辑视频（剪辑/配乐/字幕）
│  ├─ ✓ 分享视频
│  └─ ✓ 删除视频
│
└─ ⚙️ 通用管理
   ├─ ✓ 搜索媒体（按名称/时间/标签）
   ├─ ✓ 筛选排序（时间倒序/类型/大小）
   └─ ✓ 相册分类（新建/重命名/删除）
```

> 💡 使用场景：需求分析完成后、画原型前，用于梳理功能清单，避免遗漏

## 二、抽象方法论（可迁移的核心逻辑）

### 🎯 方法论1：先分类，再绘图——明确结构图的「类型-目的」映射

```
┌─────────────────────────────────┐
│  你要解决什么问题？              │
├─────────┬─────────┬─────────────┤
│ 功能结构图 │ 信息结构图 │ 产品结构图  │
├─────────┼─────────┼─────────────┤
│ 能做什么？ │ 展示什么？ │ 怎么呈现？  │
│ 梳理功能清单│ 设计内容字段│ 指导原型绘制│
│ 动词导向   │ 名词/字段导向│ 页面+操作导向│
└─────────┴─────────┴─────────────┘
```

> ✅ 关键：先问目的，再选工具，避免用错结构图类型

---

### 🎯 方法论2：分层拆解——MECE原则落地

**拆解逻辑：What → Where → How**

```
第1层：产品/核心模块（What：我们要做什么产品？）
   ↓
第2层：子模块/业务领域（Where：功能属于哪个业务场景？）
   ↓
第3层：具体功能/操作（How：用户怎么完成这个任务？）
```

**MECE检查清单：**
- [ ] 相互独立：各子模块无重叠功能
- [ ] 完全穷尽：用户核心诉求都有对应功能承接
- [ ] 层级清晰：上层是下层的抽象，下层是上层的具体

---

### 🎯 方法论3：动词导向——功能描述的标准化

**功能 = 用户可执行的操作 = 动词为核心**

```
✅ 正确表达：
• 编辑图片 / 分享 / 删除 / 搜索 / 筛选

❌ 避免表达：
• 图片编辑功能 / 分享模块 / 删除按钮（名词化/UI化）

💡 技巧：
• 名词可省略（上下文清晰时）：「编辑」默认=「编辑图片」
• 语序可调整：「展示图片」=「图片展示」，保持团队统一即可
```

---

### 🎯 方法论4：时序解耦——先功能完整，再页面设计

```
🔄 标准工作流：

需求池 → 需求分析 → 方案提炼 
                    ↓
        【功能结构图】← 复杂功能必用！
                    ↓
        功能清单（PRD附件）
                    ↓
        【产品结构图】← 分配功能到页面
                    ↓
        原型设计 + 交互说明
```

> ⚠️ 常见误区：一上来就画原型，导致功能遗漏或逻辑混乱

---

### 🎯 方法论5：复杂度管理——工具使用的判断标准

| 场景           | 是否需用功能结构图 | 原因           |
| ------------ | --------- | ------------ |
| 功能点≤3个，逻辑简单  | ❌ 可跳过     | 脑内梳理即可，效率优先  |
| 功能点>5个，涉及多状态 | ✅ 建议使用    | 避免遗漏，便于评审    |
| 多角色/多端/多流程   | ✅ 必须使用    | 复杂度管理，降低沟通成本 |
| 需求频繁变更       | ✅ 推荐使用    | 结构图便于迭代和追溯   |

---

### 🎯 方法论6：迭代思维——结构图是动态资产

```
🔄 结构图生命周期：

V1.0 快速罗列 → 保证功能完整性（头脑风暴式）
   ↓
V1.1 评审对齐 → 与研发/业务确认边界（查漏补缺）
   ↓
V1.2 细化补充 → 增加异常流程/边界情况（如空状态、网络错误）
   ↓
V2.0 归档沉淀 → 作为PRD附件+知识库素材（便于新人上手）
```

---

## 📌 一句话总结

> **功能结构图的本质**：用「分层+动词」的方式，把「用户能做什么」结构化呈现，服务于功能清单梳理，是连接「需求分析」与「原型设计」的关键桥梁。

**使用口诀**：先分类、再拆解、动词写、后页面、复杂必用、动态迭代 ✅
